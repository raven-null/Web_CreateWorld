## 1. 本版新增的需求（变更摘要）

| # | 需求 | 转换成的设计 |
|---|------|--------------|
| 1 | 白板长宽有限制，就像地球有限制；**档位要能自由选择，还要能放大缩小** | 数据以「定尺全球白板」为唯一真源：**宽度自由输入 512~16384（默认 2048），高度自动为一半**（2:1 是「白板 = 地球」的唯一硬约束）；**视图缩放自由连续（适应窗口 ~ 32×）**，白板本身也可改尺寸（§5.6，×2 幂次反复改完全无损） |
| 2 | 白板可以转换成 3D 地球仪 | 白板是**等距圆柱投影**下的球面展开，经纬度是唯一坐标真源；3D 地球仪只是同一数据的另一种呈现（球面贴图 + 交互旋转 + **大气辉光 / 星空背景 / 昼夜明暗**），**不产生第二份数据** |
| 3 | 白板有多个图层（政治 / 军事 / 宗教 / 民族…），要能加图层 | 引入**图层系统**：图层可自由增删、命名、选类型、调顺序与透明度；地形用栅格笔刷，专题图层（国界 / 战线 / 势力范围）用矢量对象 |
| 4 | 一份部署在网站，一份做成应用，功能不能变 | **共享包（core / storage）+ 三处平台适配**：渲染抽象、存储适配、压缩能力抽象、导出能力抽象；产物同源（WebView），3D 与快捷键走优雅降级而非功能删减 |
| 5 | 画的时候要能知道「已画的区域有多大」，别不知不觉造出庞然大物 | 引入**比例尺与尺度系统**（第 7 章）：等距圆柱下比例尺随纬度变化，必须按光标纬度实时换算；提供自适应比例尺、绝对尺寸换算、距离与面积测量、笔触统计、真实世界对照参考 |
| 6 | 地图编辑器要**独立出来**，做成「小插件」——可单独升级，也能装到其他项目上 | 拆成 `map-core` / `map-editor` / `map-editor-web` 三个包，宿主通过 `MapHostAdapter` 注入存储、通过 `theme` 注入视觉（第 15 章）：**插件不假设后端、路由、主题、登录与框架** |
| 7 | 专题图层要按**比例尺**决定显示什么 | 「什么比例尺显示什么」是地图软件的专业感来源：国界与国名在小比例下保留、村落与细节符号在大比例下才出现（§10.3）——**判据用「对象在屏幕上的像素尺寸」**，用户不需要换算 km/px |
| 8 | 3D 地球仪要**好看**：大气辉光、星空背景、昼夜明暗 | 全部自写着色器实现（菲涅尔辉光 + 程序化星空 + 黄昏线），零新依赖；三项独立开关 + 三档性能降级（§14.3），且**配色克制**，不做炫彩壁纸 |

> 前两项合起来其实是一条设计主线：**坐标系定了，2D 与 3D 就都只是视图**。第三项决定了数据结构从「一张图」变成「一本图集」。第四项决定了代码必须分层——凡是能放进共享包的逻辑，绝不允许写在页面里。第五项要求**尺度是一等公民**：地图软件的手感，一半来自「知道自己在画多大」。第六项则是最硬的一条**架构纪律**：插件从第一天起就不认识主站，否则「独立出去」会变成重写。第七、八项是对**「专业感」**的投入：前者让地图在任何缩放下都读得懂，后者让 3D 视图拿得出手——两者都做成可关、可降级，不绑架基础功能。

## 2. 目标与范围

### 2.1 一句话目标

作者**不依赖任何绘图软件**，在网页或桌面 / 手机应用里用「草地笔刷 / 海洋笔刷 / 山脉笔刷」涂抹出自己的世界，用**图层**叠加政治、军事、宗教、民族等专题信息，随时把世界**转成 3D 地球仪**端详，一键导出成成品图片。

### 2.2 使用场景

| 场景 | 描述 |
|------|------|
| 从零造世界 | 新建 2048×1024 全球白板 → 海洋打底 → 涂大陆轮廓 → 补草地、沙漠、森林 → 叠山脉 → 切成 3D 地球仪看看比例 |
| 边画边量 | 涂完一块大陆后看底部统计「占全球陆面 6%、约 810 万平方公里」，立刻知道这不是大陆而是超大陆，趁早收笔 |
| 叠加政治 | 新增「政治」图层 → 画国界与势力范围 → 新增「军事」图层 → 画战线与进军箭头 → 一键隐藏军事图层给别人看干净版 |
| 多视角端详 | 切 3D，旋转到赤道正面截图；回 2D，导出一张 2:1 海报图 |
| 换设备继续 | 在电脑上画一半，手机上打开同一张图继续（数据一致，交互按触屏优化） |

### 2.3 本期范围与不做的事

| 项目 | 决定 |
|------|------|
| 起点 | **空白球面白板**（程序化绘制），保留原有「上传图片」地图类型 |
| 白板形态 | **宽度自由输入**（512~16384，规整到 128 的倍数），高度自动 2:1；**不做**任意长宽比的矩形画布（§5.1 有理由） |
| 视图缩放 | 自由连续（适应窗口 ~ 32×），光标锚点缩放，按区间切换采样（§5.6.1） |
| 白板改尺寸 | 支持（§5.6.2）：最近邻重采样 + 分批上传 + 无损情形提示；×2 幂次改尺寸零损失 |
| 绘制方式 | 地形图层的**笔刷涂抹**（栅格）+ 专题图层的**矢量对象**（二期） |
| 2D / 3D | 同一数据双向切换；3D 为只读浏览（首期不做球面上绘制），含**大气辉光 + 星空背景 + 昼夜明暗**（各可单独关闭） |
| 图层 | 首期支持**新增 / 改名 / 选类型 / 排序 / 显隐 / 透明度 / 删除**；类型预设齐备，专题图层的**编辑工具**二期落地 |
| 比例尺显示规则 | ✅ 首期做：图层级 + 对象级显示条件（按屏幕像素判据），预设齐备；**标签自动避让**列入二期（§10.3） |
| 尺度比例尺 | 首期支持**自适应比例尺、光标处经纬度与实距、天体半径设定、距离标尺工具、笔触与总面积统计、真实世界对照、阈值可调的尺度预警**；球面多边形面积测量二期落地（见第 7 章） |
| 标记整合 | ✅ 现有 `markers` 整合进同一画布，并升级为「可归属图层的锚点对象」 |
| 多人同时编辑 | ❌ 不做实时协同，仅用版本号冲突保护 |
| 极区变形 | 不做极地方位投影，接受等距圆柱在高纬度的横向拉伸（见 §9.4） |
| 底图滤镜 / 切片拼接 | 不做 |

### 2.4 可行性结论

**可以实现，且不需要引入任何付费服务。**

- 零信用卡约束：数据存 Cloudflare D1，笔刷与 3D 全部在客户端完成，服务端只做存储与校验 → ✅
- 免费额度：栅格按瓦片增量写、gzip 压缩、空瓦片不落库；单次保存仅几 KB～几十 KB → ✅ 见 §12.3
- 3D 地球仪：**球面贴图 = 平面白板**（等距圆柱投影），WebGL 球体渲染是标准做法，不需要额外数据或服务 → ✅ 见 §14
- 多端一致：Tauri / Capacitor 都是 WebView 壳，**产物同源**（`方案.md` 10.1 已定），把平台能力抽成三处适配即可 → ✅ 见 §15.9
- 独立成插件：编辑器的全部依赖都可以抽象成「一个适配器 + 一包主题 token」，不依赖主站的后端、路由、登录与业务概念 → ✅ 见 §15
- 唯一硬约束是 **D1 单库 500MB 与单行 2MB**，通过瓦片化 + 尺寸上限规避 → ✅ 见 §6
- 插件化本身不增加运行成本：只是把代码放在独立包里并约束依赖方向，**不引入新服务、新依赖、新构建链路** → ✅

## 4. 核心设计决策

| # | 决策 | 理由 |
|---|------|------|
| 1 | **经纬度是唯一坐标真源**，平面像素与球面坐标都由它派生 | 2D 与 3D 必须共用一份数据，否则一切「切换」都要做数据转换与对账 |
| 2 | 平面视图采用**等距圆柱投影**（经纬度 → 等距网格） | 球面 ↔ 平面线性可逆、换算无浮点坑；且「平面白板 = 球面贴图」，3D 直接可用 |
| 3 | 尺寸**自由选、比例必须 2:1**：宽度 512~16384 任意，高度自动为一半 | 2:1 才是一套完整经纬网；非 2:1 无法无缝贴到球面、像素不再是正方形（§5.1）——「自由」与「球面」的唯一折中点 |
| 4 | 视图缩放**自由连续**（连续值，不是整数倍），白板改尺寸则是显式操作 | 前者是「看」不碰数据，后者是「变」要重采样；两者界面分开、文案分开（§5.6） |
| 5 | **经度环绕**（东西接缝相连），纬度不环绕 | 地球就是一圈；笔刷跨接缝时要正确落笔，否则地图会出现一条假边界 |
| 6 | 地形用**调色板索引栅格 + 分瓦片**，专题图层用**矢量对象** | 涂抹需要像素级自由；国界 / 战线需要可编辑的控制点、缩放不失真、数据量小 |
| 7 | 图层是**数据**不是代码：一张 `map_layers` 表 + `type` 字段 | 需求 3 的「可以加图层」意味着用户随时新建「外交」「经济」等新图层，写死枚举会立刻不够用 |
| 8 | 首期做完整**图层框架**+地形绘制，专题图层的**编辑工具**分期落地 | 框架对了，后面每加一种图层类型只是加一个渲染器与工具，不返工 |
| 9 | 跨端：**共享包放逻辑，平台只提供能力** | 一份代码三端跑，功能靠「优雅降级」而非「平台差异」 |
| 10 | 3D 首期只读（浏览 / 旋转 / 截图） | 球面绘制涉及拾取与投影反解，风险大收益小；先把「看」做到位 |
| 11 | 本地优先 + 显式保存（绘制期间零网络请求） | 省 D1 写额度，涂抹零卡顿，离线也能画（多端必需） |
| 12 | **尺度是一等公民**：任何时刻都能回答「这块地有多大」 | 用户不知道自己在造多大的东西，就会造出不可用的世界；比例尺、面积统计、真实世界对照必须是常规 UI 元素而非隐藏功能 |
| 13 | 所有比例尺换算只依赖「天体半径」一个参数，且**不落进栅格数据** | 半径改变不影响已画内容（经纬度不变），无需重绘或迁移数据 |
| 14 | 编辑器是**独立插件**：不 import 主站、不假设后端与主题、不直接 fetch | 「独立出去」要从第一天就是事实，而不是事后的重构（§15.1） |
| 15 | 宿主与插件之间只有两个契约：`MapHostAdapter`（数据）与 `MapEditorTheme`（视觉） | 接口面越小，越容易被别的项目接进去；也越容易长期维护 |
| 16 | 数据可整体导出为**自包含快照**（含瓦片 base64） | 装到别的项目时数据能跟着走，不被某个后端锁死（§15.7） |

## 5. 白板：尺寸、投影与坐标系统

### 5.1 白板尺寸：自由选择 + 唯一约束 2:1（需求 1）

用户**自由输入宽度**，高度自动为一半——这是整套设计里唯一不能让步的约束，理由见下。

```
宽度 W：整数，512 ≤ W ≤ 16384（**默认 2048**）
高度 H = W / 2      ← 自动，不可单独输入
```

**默认值已定案：2048×1024**（≈19.6 km/px，桌面与移动端共用同一默认值；用户新建时可自由修改宽度）

| 宽度档位（参考） | 内存（单层） | 每像素实距（地球，赤道） | 适合画到 |
|------------------|--------------|--------------------------|----------|
| 512×256 | 0.13 MB | ≈ 78 km/px | 势力轮廓草图 |
| 1024×512 | 0.5 MB | ≈ 39 km/px | 大洲级布局 |
| **2048×1024（默认）** | 2 MB | ≈ 19.6 km/px | 大陆 + 国界 |
| 4096×2048 | 8 MB | ≈ 9.8 km/px | 国界 + 主要城市 |
| 8192×4096 | 32 MB | ≈ 4.9 km/px | 行省 + 城市 |
| 16384×8192 | 128 MB | ≈ 2.4 km/px | 上限，桌面端专用，需强提示 |

- **高度自动取值**：界面上只有一个宽度输入框，高度显示为一旁只读的灰字
- **输入宽度会被规整**：向上取整到 **128 的倍数**——256 的瓦片整除、同时保证「宽是 2 的倍数」以兼容旧标记（`markers.x/y` 是 0~1 比例，与分辨率无关，所以规整不影响已有标记）
- **为什么必须 2:1**：等距圆柱投影下 360° 经度 : 180° 纬度 = 2 : 1。只有保持这个比例，平面白板才**恰好等于一套完整球面贴图**——3D 地球仪才能无缝（第 14 章），**像素才是正方形**（经、纬两方向的每像素实距数值相同，画圆不用纠正为椭圆，比例尺与测量误差模型才简单，第 7 章）
- 若不锁 2:1：球面会出现重复或缺口，比例尺要分方向各算一套，测量与面积全部要改写——**代价远大于收益**，因此不做「任意长宽矩形」

**尺寸与画质的关系**：白板尺寸决定**地图的最大信息量**（每个像素在数据上就代表一块地方，后期无法凭空造出细节）。因此编辑器在新建时就把「你选的尺寸对应能画到什么程度」用表格摊开（见上表最后一列），并在 07.7 的尺度预警里对「画了超出该尺寸承载能力的细节」给出提示。

- 白板之外没有世界：所有绘制都被限制在板内；纬度方向是真实的南北极边界，经度方向首尾相连
- 存储的是**经纬度栅格**，与白板尺寸解耦：改尺寸只是重采样（§5.6），坐标语义不变
- 上表按**地球半径 6371 km** 计算；若世界是更大的行星，实距等比放大（见第 7 章）

### 5.2 投影：等距圆柱（需求 2 的数学基础）

```
经度 lon ∈ [-180, 180]  →  平面横坐标 u = (lon + 180) / 360 ∈ [0, 1]
纬度 lat ∈ [-90, 90]    →  平面纵坐标 v = (90 - lat) / 180 ∈ [0, 1]
平面像素                →  px = u × W，py = v × H
```

反解同样线性：`lon = u × 360 - 180`，`lat = 90 - v × 180`。

选择它的三条理由：

1. **平面图就是球面贴图**，3D 地球仪直接把它贴上去即可，不需要重投影或生成第二份纹理
2. 换算线性、无奇异点，笔刷落点与拾取都简单，浮点误差不累积
3. 全世界统一的「正射经纬网格」观感，与项目「档案馆 / 编年史」的冷静气质相符

### 5.3 与球面坐标的换算

```
φ = lat × π / 180,  λ = lon × π / 180
x = R · cos φ · sin λ
y = R · sin φ
z = R · cos φ · cos λ
```

球面 → 屏幕用常规透视投影（相机在球外）；拾取时把屏幕射线与球面求交，反解出经纬度供未来「在球上放标记」使用。

### 5.4 经度环绕的处理约定（必须显式实现）

| 环节 | 约定 |
|------|------|
| 笔刷落点 | 经度取模回绕（`lon = ((lon + 180) % 360 + 360) % 360 - 180`） |
| 跨接缝的笔刷 | 若笔刷圆形 / 方形覆盖到板的两端，**两端都要落笔**（否则接缝处出现缺口） |
| 瓦片寻址 | 列号取模环绕；纬度方向越界直接丢弃（极外无内容） |
| 视图平移 | 经度方向允许连续环绕平移（可选开关，默认开） |
| 图层叠放 | 与环绕无关，图层间不做地理裁剪 |

### 5.5 局部地图 vs 全球白板的取舍（重要）

需求 1 说的是「像地球一样有限制」，因此**主模式定为全球白板**。若以后要画「某块大陆的详图」，不引入第二套坐标系，而是：

- **同板放大**：调高白板分辨率（§5.6.2 的「白板改尺寸」，如 2048 → 4096 / 8192），在同一张全球图上精细绘制
- **视野书签**：保存若干「视野预设」（黄道带式的区域框），一键跳到某区域（Phase 3 的多级地图，见 §14）

> 反过来说：**不建议**做「任意矩形范围的局部地图」，那会让同一块地方存在两套数据，2D 能看、3D 要补，图层还要做地理裁剪，复杂度陡增。

### 5.6 视图缩放与白板改尺寸（容易混淆，必须分开）

> 这是**两件完全不同的事**，界面上要分开，文档里也不能混：
>
> | | 视图缩放（看） | 白板改尺寸（变） |
> |---|---|---|
> | 改变什么 | 只在屏幕上放大缩小 | 改变地图本身的分辨率 |
> | 影响数据 | 无 | 重建全部瓦片、重采样 |
> | 是否要保存 | 不需要 | 需要，且 revision +1 |
> | 耗时 | 实时（每帧） | 秒级（分批上传） |
> | 谁需要关心 | 只是操作体验 | 决定地图的「信息容量上限」 |

#### 5.6.1 视图缩放（自由缩放，不是整数倍）

**缩放范围**：适应窗口 ~ 32×，自由连续（滚轮 / 双指捏合 / `+` `-` 按钮 / 双击重置）。

采样策略（这是清晰度与性能的关键）：

| 缩放区间 | 采样 | 理由 |
|----------|------|------|
| `zoom < 1`（看全图） | `imageSmoothingEnabled = true` | 缩小看全貌时平滑更好看，也能看清整体形状 |
| `1 ≤ zoom < 8` | `imageSmoothingEnabled = false` | **像素完美**：一格数据 = 整数个屏幕像素，像素风的关键 |
| `zoom ≥ 8` | 可切换「像素平滑」 | 放到 32× 时单格已占 32×32 屏幕像素，开平滑能看出软过渡，便于对齐与精修（32× 下 1024 白板只覆盖 32×16 格视野，正是细修小区域时需要的） |

- **只重绘可见视野内的瓦片**：`zoom` 越大需要绘制的瓦片越少，所以放大反而更快；缩到最小时瓦片最多，此时按屏幕分辨率先合成到一张缓存图再绘
- 缩放以**光标位置为锚点**（滚轮缩放时光标下的地理点不动），这是地图类工具的基本手感要求
- 缩放级别与视口中心一起进 URL / 状态（`?lon=&lat=&z=`），便于分享「我正在看的这一块」，也与 §16.3 的 2D↔3D 视野锚点同步共用同一套参数
- **不影响绘制精度**：落笔时先按 `zoom` 反算平面像素再换算经纬度，任何非整数 zoom 都不累积误差
- 触屏：双指捏合缩放，**单指绘制与双指缩放要能同时工作**（用 pointer 事件计数判断，避免绘制中途误变成缩放）

#### 5.6.2 白板改尺寸（重采样）

入口：`地图设置 → 白板分辨率 → 修改`。

**流程**

1. 输入新宽度 → 自动规整到 128 的倍数 → 预览显示「2048×1024 → 3000×1500，像素尺寸 ×1.46，预计数据量 ×2.1」
2. 确认对话框列出后果：瓦片数、预计体积、矢量对象数、**是否会有细节损失**（缩小情形）
3. 确认后：客户端读出全部瓦片 → 重采样 → 分批上传 → 服务端写入新尺寸与新瓦片、删除不再需要的旧瓦片 → `revision +1`、更新 `updated_at`
4. 其他打开着这张地图的端会因 revision 变化收到「地图已被修改，请重新加载」提示（沿用 §12.4 的冲突机制）

**无损的情形（要主动告诉用户）**

| 变化 | 数据结果 | 说明 |
|------|----------|------|
| ×2 的整数幂缩放（2048→4096、4096→2048） | **完全无损** | 每格 1×1 或 2×2 对齐，相当于位运算 `<<1` / `>>1`，无插值 |
| 其他整数倍（如 2048→6144，×3） | 基本无损（有轻微几何错位） | 边界会落在非整数格上，需最近邻取整 |
| 非整数倍放大（2048→3000，×1.46） | 无损但**没有新增信息** | 只是把像素放大，锯齿边缘更明显；想提升画质应当**重画**而不是放大 |
| 非整数倍缩小（3000→2048） | **会丢细节** | 细的河流、小岛可能消失；必须给明确警告 |

**实现要点**

- **栅格重采样用最近邻（Nearest Neighbor）**：调色板索引图只有 8 位，双线性插值会算出「调色板里不存在的中间色」，反而污染数据。放大时整块复制原格；缩小时取目标格覆盖区域的中心格（可选：对 2×2 以上的缩小窗口做一次**众数投票**，避免出现孤立的错误色点）
- **矢量对象不用重采样**：它们存经纬度，与分辨率无关；但线宽要定义在**屏幕空间**（如「2 屏幕像素」），否则放大白板后线条会显得过细
- **标记（`markers`）也不受影响**：`x / y` 是 0~1 相对比例，天然与分辨率解耦
- **分批与幂等**：大改尺寸可能涉及几千个瓦片，按 §12.4 的分批上限（32 / 批）提交并显示进度；服务端在写入前先校验（是否 2:1、是否在 512~16384 内、瓦片行列数是否与尺寸匹配），任一批失败则整体回滚并保留原白板
- **`k₀` 随之变化**：分辨率一变，每像素实距立即变化，比例尺与面积统计自动重算——这正是「数据存经纬度」的红利（§4 决策 13）：**改尺寸不需要改任何尺度逻辑**

**性能预算**

| 操作 | 目标 |
|------|------|
| 2048 → 4096（无损放大） | ≤ 3s（含上传） |
| 4096 → 2048（缩小采样） | ≤ 4s |
| 超大（16384 档）改尺寸 | 桌面端专用，显示明确进度与「请勿关闭标签页」提示 |

### 6.3 瓦片划分（经纬网分块）

- 每瓦片 **256×256** 像素，整个白板为 `cols × rows` 网格（2048×1024 → 8×4 = 32 个瓦片/图层）
- 列环绕、行不环绕（§4.4）
- **空瓦片不落库**：全透明瓦片 = 表中无行，读取时缺失即视为空
- 一次保存只提交脏瓦片（通常 1～4 个）

### 6.4 瓦片二进制格式 `cwt1`

```
魔数 "CWT1" (4B) | 宽 (2B, LE) | 高 (2B, LE) | 压缩标识 (1B) | gzip(索引字节流，行优先)
```

- 压缩标识：`0` = 原始字节，`1` = gzip。**两种都要支持**（理由见 §14.3：并非所有平台都有 `CompressionStream`）
- 之所以不用 PNG：Worker 的 `DecompressionStream` 只支持 gzip / deflate，解 PNG 需要额外引入 zlib 实现；自定义格式服务端零依赖、可校验、可增量
- 编解码器放在 **`packages/map-core`**（纯函数、零平台依赖、零宿主概念），三端与所有宿主共用同一份实现，避免「网站能开、应用打不开」这类兼容问题

## 7. 比例尺与尺度系统（需求 5）

> 目标：**任何时刻都能回答「我刚画的东西有多大」**。这是手感问题，不是附加功能——不知道尺度，用户就会在 2048 的白板上涂出一块比地球还大的大陆，等到发现时已经画了几小时。

### 7.1 为什么不能只放一根固定的比例尺条

因为**等距圆柱投影下比例尺随纬度变化**，这一点无法回避：

- 白板横向固定代表 360° 经度，而每 1° 经度对应的实际距离是 `(πR/180) × cos(纬度)` —— 越靠近两极越短
- 白板纵向固定代表 180° 纬度，每 1° 纬度对应 `πR/180` —— **不随纬度变化**

所以同一根 200px 的比例尺条，在赤道代表 3910 km，在北纬 60° 只代表 1955 km。**比例尺必须按光标纬度实时计算**，这是本设计最关键的一条。

### 7.2 两个方向的比例尺公式

以白板宽 `W`、高 `H`、天体半径 `R`（单位 km）为例：

```
纬度方向：1 px = πR / H                                   （恒定，与纬度无关）
经度方向：1 px = 2πR / W × cos(lat)                       （赤道最长，两极趋近 0）
```

推理：横向一整圈覆盖 360° 经度，长度 = 圆周 = `2πR`，分到 `W` 列 → `2πR / W`；
纵向覆盖 180° 纬度，长度 = 半圈 = `πR`，分到 `H` 行 → `πR / H`。

由 2:1 白板（`W = 2H`）可得一个重要结论：

> 两个方向的数值相等：`2πR / W = πR / H` —— 这就是**像素是正方形**的含义（与 §5.1 一致）。
> 于是「赤道每像素实距」可以统一写成 **`k₀ = 2πR / W = πR / H`**，全文与实现都只用这一个基准量。

代入地球（`R = 6371`）：

| 白板宽 W | `k₀`（赤道每像素，两方向相同） | 北纬 60° 的经度方向 |
|----------|------------------------------|---------------------|
| 1024 | 39.09 km/px | 19.55 km/px |
| 2048 | 19.55 km/px | 9.77 km/px |
| 4096 | 9.77 km/px | 4.89 km/px |
| 8192 | 4.89 km/px | 2.44 km/px |

> 上表与 §5.1 的档位表一致（那张表列的是「每像素实距」，2048 档为 19.6 km/px）。
> ⚠️ 早期草稿里把系数写成 `πR` 而非 `2πR`，会让所有读数偏小一倍——已由单元测试锁定（地球 + 2048 白板：赤道 19.55 km/px、横向总长 40030 km）。

**参考值（判定比例尺是否"合理"的标尺）**：地球赤道周长 ≈ 40030 km；经线半圈（极到极）≈ 20015 km；1° 纬度 ≈ 111.19 km。这三个数字已经写进单元测试。

### 7.3 天体半径：尺度的唯一参数（§4 决策 13）

`maps.radius_km` 决定所有实距换算，默认 6371 km（地球）。

| 预设 | 半径 | 说明 |
|------|------|------|
| 地球 | 6371 km | 默认 |
| 火星 | 3390 km | |
| 月球 | 1737 km | |
| 自定义 | 任意 | 架空世界主场 |

- 半径改变**不需要重绘、不需要迁移数据**（栅格与对象存的是经纬度），只是所有显示数值重新计算 → 鼓励用户随时调整手感
- 反向约束（防止笔刷相对世界过粗）：最小笔刷边长 1 px（1024 白板下 1 px ≈ 39 km）。若用户把半径设到 1000 km，其 1 px ≈ 6 km、笔刷最小 1 px 也相当于 6 km，1 px 笔刷可以精细绘制，因此**必须支持 1 px**——但 1 px 绘制手感极差，因此当 `k₀ > 20 km/px` 时提示「白板精度较低，建议提高白板分辨率（§5.6.2）或增大半径」——即 **1024 宽建议半径 ≥ 2000 km**、**2048 宽建议 ≥ 4000 km**
- 未来可扩展为多天体（每张地图独立半径参数），本期不做

### 7.4 自适应单位（默认三档，可扩展）

> **已定案**：默认单位链为 **km / AU / 光年**；自定义单位（里、丈等）**列为后续可更新功能**，因此单位系统从第一天就按「可扩展的数据表」实现，而不是写死三个分支。

`k₀` 的数值跨度可能极大（从行星级到星系级），因此单位按需切换，避免出现「2.1e7 公里」这种不可读的数字：

| `k₀` 范围 | 主单位 | 辅助 |
|-----------|--------|------|
| < 1000 km/px | 千米（km） | 米（m）用于极精细的白板 |
| 1000 ~ 1e8 km/px | **天文单位 AU**（1 AU ≈ 1.496e8 km） | 地球直径（12742 km）作为对照 |
| ≥ 1e8 km/px | **光年**（1 ly ≈ 9.461e12 km） | 日地距离作为对照 |

对照参考物在 UI 里自动选取最接近的一档：地球直径 / 地月距离 / 日地距离 / 太阳直径 / 光年。

**为「以后可更新」预留的实现方式**

单位不做成 `if/else`，而是一张**单位注册表**——新增单位、调整阈值、甚至让某个世界用自己的「里 / 丈」，都只是往表里加一项：

```ts
/** 单位定义：换算基准统一为 km */
interface DistanceUnit {
  id: string;                 // "km" | "au" | "ly" | 自定义
  name: string;               // 显示名：千米 / 天文单位 / 光年
  symbol: string;             // km / AU / ly
  kmPerUnit: number;          // 1 单位 = 多少 km
  showBelowKm: number;        // k₀ 小于该值时选用本单位（注册表按此排序）
  reference: string[];        // 该单位下的对照参考物 id 列表
}
```

- 默认注册表只注册 `m / km / AU / ly` 四项，即可满足 §7.9 的全部验收
- 将来加「里」「丈」只需追加条目 + 一个换算值；若要做成**世界级设定**（每个世界用自己的度量衡），把注册表挂到 `maps` 的配置里即可，比例尺、测量工具、面积统计**都不需要改代码**
- 单位只在**显示层**生效：内部一律以 km 计算，因此换单位不影响任何已有数据（与 §4 决策 13 同一个思路）

### 7.5 距离与面积的正确算法（投影陷阱，必须显式处理）

**① 屏幕直线 ≠ 球面最短路径**

在等距圆柱平面上，「屏幕上看着是直线」的一条斜线，在球面上**不是测地线**（只有赤道与经线是）。因此：

- 测量两点距离时用 **haversine**（或等价的球面余弦公式），不要用「像素距离 × 比例尺」估算长距离
- 同一纬度上沿纬线测量时，可直接用 `Δlon × (πR/180) × cos(lat)`
- 界面须标注：「2D 视图中的直线在球面上是曲线，精确距离请以数值为准（3D 视图可直观看到）」

**② 面积必须按纬度带加权**

等距圆柱投影下，每个像素代表的实际面积随纬度递减：

```
像素面积(lat) = k₀² × cos(lat)          （km²）
```

所以「像素计数 × 常数」是错的，必须逐纬度带加权求和（实现见 §7.6）。

**③ 变形倍率要可视化**

| 纬度 | 局部拉伸（相对赤道） | 面积放大 |
|------|----------------------|----------|
| 0° | ×1.00 | ×1.00 |
| 30° | ×1.15 | ×1.15 |
| 60° | ×2.00 | ×2.00 |
| 80° | ×5.76 | ×5.76 |

- 底部信息条常驻显示当前光标纬度的**变形倍率**
- 变形倍率 > 2 时给出明确提示：「高纬度横向拉伸 ×N，此处尺寸不宜直接目测」；3D 视图可直观核对
- 这是等距圆柱固有的代价（§9.4），不通过换投影解决，而是**让用户看得见**

| **自适应比例尺条** | ✅ | 浮动在地图左下角，按光标纬度实时换算；取整数距离（100 / 500 / 1000 / 5000 km），长度 = `单位距离 / 当前比例尺` |
| **光标实距读数** | ✅ | 信息条常驻：经纬度、`k₀`、当前纬度每像素实距、变形倍率 |
| **笔触统计** | ✅ | 每笔记录覆盖像素数与地形类型；配合调色板显示「本次笔触覆盖 ≈ X 万 km²」 |
| **图层面积统计** | ✅ | 按地形类型汇总：陆地 / 海洋 / 沙漠各占多少 km² 与全球百分比 |
| **测量工具（折线距离）** | ✅ | 工具条新增「测量」：点击落点、实时显示累计距离与方位角、双击结束；支持多段折线 |
| **真实世界对照** | ✅ | 面积与距离自动给出类比：「≈ 1.4 个澳大利亚」「≈ 中法面积之和」；架空世界则以「占全球陆地 X%」为主 |

| **球面多边形面积** | 二期 | 矢量对象（势力范围 / 分布面）的精确面积：球面多边形面积公式，误差 < 0.5% |
| **方位角与测地线** | 二期 | 大圆航线绘制、终点方位角；解决「直线在球面上是曲线」的绘制需求 |

**统计的实现方式（性能关键）**

- 客户端：`TileStore` 维护 `Uint32Array` 计数数组（`索引 × 数量`），落笔时按覆盖范围**增量累加**，撤销时反向扣减——**绝不扫描全图**
- 服务端：`maps.stats` 保存权威副本；每次保存瓦片时按脏瓦片 + 保存前后的哈希差异增减计数，并做一次轻量自检
- 修复机制：设置里提供「重新统计」按钮（全图扫描补正），用于异常情况

### 7.7 尺度预警规则（「别造出庞然大物」的具体实现）

| 触发条件 | 默认阈值 | 提示 |
|----------|----------|------|
| 单块连通陆地占全球面积 | > 15% | 「这块大陆占全球 15%（≈ 7700 万 km²，比亚洲还大）——确定不是把海涂成了陆地？」 |
| 全球陆地占比 | > 45% | 「陆地占全球 45%，地球只有 29%——如果这是海洋世界需要调整」 |
| 单一国家（政治图层）面积 | > 3000 万 km² | 「该国面积超过俄罗斯（1710 万 km²）」 |
| 白板精度 `k₀` | > 20 km/px | 「白板精度较低，建议提高白板分辨率或增大半径」（§7.3、§5.6.2） |
| 变形倍率 | > 2 且正在绘制 | 「此处高纬变形 ×N」（§7.5 ③） |

- 提示一律用**可关闭的非阻断式提醒**（顶部横幅 / 信息条变色），绝不弹窗打断创作
- 判断阈值是**启发式**而非硬约束：架空世界本就可能反常识，提示只负责「让用户知道」，不负责阻止

#### 7.7.1 阈值可调 + 可整体关闭（已定案）

**原则：常识是默认值，不是法律。** 用户的设定超出地球常识时，有权关掉这套常识，按自己的想法来。

**三档预设（默认「按地球常识」）**

| 模式 | 行为 |
|------|------|
| **按地球常识**（默认） | 用上表的阈值提示 |
| **宽松** | 阈值放大到 2 倍（陆地 30% / 全球 60% / 国家 6000 万 km²），只在极端离谱时提醒 |
| **关闭** | 不再提示任何尺度预警；**比例尺、实距读数、面积统计照常工作** |

**自定义阈值**：三种规则各自的判据值可单独改，改在**地图级**而不是全局——因为一个账号下可能同时存在「类地球世界」和「超大陆世界」，全局开关必然两边不讨好。

**只关「常识判据」，不关「客观读数」**（这条要写进界面文案里）

| 类别 | 例子 | 是否可关 |
|------|------|:--------:|
| 启发式判据 | 「比亚洲还大」「超过俄罗斯」「地球只有 29%」 | ✅ 可调 / 可关 |
| 客观读数 | 每像素实距、经纬度、变形倍率、面积数值、比例尺条 | ❌ 始终显示（否则用户失去判断依据） |
| 精度提示 | `k₀ > 20 km/px` 提示提高分辨率 | ✅ 可关，但默认保留（它关系到操作手感，不是世界观设定） |

**交互落点**

- 每条提示自带两个快捷操作：**「知道了」**（关闭本条 30 天，按地图记）与**「不再提示这类」**（直接把该规则设为关闭）
- 完整设置在「地图设置 → 尺度提示」里，三档预设 + 逐条阈值输入框 + 一个「恢复默认」按钮
- 配置随地图存储（`maps.scale_hints`），并进快照（§15.7），因此**换项目 / 换后端也保留用户的偏好**；若将来做成世界级设定，只需把这个字段的读取顺序改成「世界 → 地图」两级回退

**实现落点**

```ts
/** 尺度提示配置：阈值集中在此，规则函数不得写死数字 */
interface ScaleHintConfig {
  mode: "earth" | "loose" | "off";     // 三档预设
  landmassPercent?: number;            // 默认 15
  globalLandPercent?: number;          // 默认 45
  countryAreaKm2?: number;             // 默认 3e7
  precisionKmPerPx?: number;           // 默认 20
  deformFactor?: number;               // 默认 2
  silentUntil?: Record<string, number>; // 每条规则的「30 天内不再提示」，按 mapId 记
}
```

- 规则判定放在 `map-core` 的纯函数里（`evaluateScaleHints(metrics, config)`），输入是统计结果 + 配置，输出是待展示的提示列表——**因此可以单测，也与 UI 无关**
- 默认配置写在 `map-core`，宿主与插件都无需关心

## 8. 投影与坐标系统（实现细则）

### 8.1 四套坐标的关系

| 坐标 | 范围 / 单位 | 用途 | 换算 |
|------|-------------|------|------|
| 经纬度 `(lon, lat)` | 度 | **唯一真源**，所有落库数据 | — |
| 平面归一化 `(u, v)` | 0~1 | 与 `markers.x / y` 兼容 | `u = (lon+180)/360`、`v = (90-lat)/180` |
| 平面像素 `(px, py)` | 0 ~ W / H | 2D 画布绘制 | `px = u×W`、`py = v×H` |
| 球面 / 屏幕 | 视角相关 | 3D 地球仪渲染与拾取 | 见 §4.3 |

> ⚠️ 现有 Leaflet 页面里存在 `y = 1 - lat / height` 的翻转（`MapsPage.tsx:163-164`），那是 Leaflet 纬度向上导致的。**Canvas 与球面渲染都不要沿用这个翻转**：本方案中 `v` 与 `y` 同向（原点在上），只有球面顶点计算时才用到纬度本身。

### 8.2 换算函数（`map-core` 纯函数，含单测）

| 函数 | 说明 |
|------|------|
| `lonLatToUV` / `uvToLonLat` | 经纬度 ↔ 平面归一化 |
| `lonLatToPixel` / `pixelToLonLat` | 经纬度 ↔ 平面像素（传入 BoardSpec） |
| `wrapLon` / `unwrapLonNear` | 经度取模回绕；保证连续性（用于笔刷跨接缝与折线绘制） |
| `lonLatToSphere` | 经纬度 → 单位球 XYZ |
| `sphereToLonLat` | 单位球 XYZ → 经纬度（3D 拾取用） |
| `featureIntersectsViewport` | 包围盒与视口相交判断（含环绕情形，用经度区间求交） |

### 8.3 环绕实现的三个坑

1. **笔刷跨界**：一次落笔同时写板的两端（左右各一次），否则接缝处出现明显缺口
2. **折线跨界**：国界跨越 ±180° 时，线段要在接缝处**断开成两段**而不是横穿整张图
3. **包围盒跨界**：`bbox_min_lon > bbox_max_lon` 表示该对象骑在接缝上，视口查询要用「两段区间」判断

| 民族 `ethnic` | 矢量 | 条纹面 + 标签 | 图层框架 ✅ | 分布面绘制 |
| 注记 `labels` | 矢量 | 纯文字 | 图层框架 ✅ | 文本工具（固定最上层） |
| 自定义 `custom` | 任选 | 由用户定 | 图层框架 ✅ | 同上 |

> **自定义图层是需求 3 的核心**：类型只是**预设模板**（决定默认颜色、默认渲染器、图例样式），用户随时能新建「外交条约」「贸易路线」这样的图层并选择栅格或矢量。所以类型字段是开放的，不写成封闭枚举。

### 9.2 图层面板交互

```
┌ 图层 ────────────────┐
│ ＋ 新增图层           │
│ ──────────────────── │
│ ☑ 注记        (文字)  │  ← 最上层
│ ☑ 军事        (矢量)  │
│ ☑ 政治        (矢量)  │
│ ☑ 民族        (矢量)  │
│ ☑ 地形        (栅格)  │  ← 最下层
└──────────────────────┘
```

- **拖拽排序**（等价于改 `z_index`）、**勾选框显隐**、**双击改名**、**滑块调透明度**
- 新增图层：填名称 + 选类型 → 给出默认样式（配色 / 图例）→ 可立即用该类型对应的工具绘制（二期）
- 删除图层：二次确认，提示「该图层的 N 个对象将被删除」；地形图层不允许全删（至少保留一个，否则白板没法画）
- 当前图层高亮；**非当前图层默认压暗显示**（15% 蒙层），避免误画到别的层
- 移动端：图层面板折叠为抽屉（与地形调色板共用抽屉位）

### 9.3 为什么地形用栅格、专题用矢量

| 维度 | 栅格（地形） | 矢量（政治 / 军事 / …） |
|------|--------------|------------------------|
| 自由涂抹 | ✅ 像素级随意 | ❌ 需要控制点 |
| 边界可编辑 | ❌ 改了只能重涂 | ✅ 拖控制点即可 |
| 缩放质量 | 依赖白板分辨率（矢量永不失真） | ✅ 无损 |
| 数据量 | 每层 ≈ 0.1～0.5 MB（gzip 后） | 一条国界 ≈ 几 KB |
| 改写成本 | 局部瓦片 | 单个对象 |

结论：**涂抹用栅格，边界用矢量**。强行统一会两边都别扭——把地形画成多边形，一笔上千顶点；把国界画成栅格，改一条线要重涂一路。

### 9.4 已知变形与取舍（等距圆柱的代价）

- 高纬度横向拉伸严重（南北极附近几乎不可用）：这是投影固有的，不做极地方位投影
- 对「画大陆与国界」的创作场景影响有限；若作者需要极区详图，走 §5.5 的「提高白板分辨率」
- 界面上给一句提示（3D 视图里高纬变形会自然显现，可视为引导）

## 10. 渲染管线

### 10.1 图层化 Canvas 分层

```
┌─ 底层 Canvas（静态）   地形栅格瓦片 + 各矢量图层的面填充，仅脏瓦片重绘
├─ 对象 Canvas（矢量）   边界线 / 路线 / 箭头 / 符号 / 注记 / 标记点，按 z_index 顺序
└─ 交互 Canvas（预览）   笔刷光标、正在绘制的笔画、选中手柄、经纬网、比例尺
```

- 只有交互层每帧重绘 → 涂抹 60fps
- 对象层按视口 + 包围盒查询拉取，滑到哪儿拉哪儿
- 图层显隐 / 透明度变化只重绘对应层（把「非当前图层压暗」做在对象层的合成参数上，避免重画栅格）

### 10.2 绘制一笔的完整流程

1. `pointerdown` → 记录起点，创建笔画命令并入 undo 栈
2. `pointermove` → 换算经纬度 → 换算像素 → 笔刷覆盖格子写入栅格 → 收集脏瓦片（含跨接缝的双落点）
3. 重绘脏瓦片区（仅交互层，当前帧效果）
4. `pointerup` → 差异块入 undo 栈 → 启动空闲计时器
5. 空闲 20 秒或用户点保存 → 提交脏瓦片（增量）

### 10.3 比例尺相关的显示规则（需求 7）

**要解决的问题**：世界全图上不该显示小村落，行省详图上又不该让国家名挤成一团。地图软件的专业感，八成来自「什么比例尺显示什么」。

**阈值用「屏幕像素」而不是「km/px」做判据**

| 方案 | 说明 |
|------|------|
| ❌ 用 `k₀`（每像素实距）当条件 | 用户要算数：`k₀ < 5 km/px` 到底对应哪个缩放级别？可读性差 |
| ✅ **用「对象在屏幕上的尺寸」当条件**（选用） | 语义就是用户看到的：*「符号边长 ≥ 6 屏幕像素时才显示」*、*「标签文字 < 11px 就隐藏」* ——所见即所得，且与白板分辨率解耦 |

界面上的滑杆用文字说明当前对应的实距（如「当前 ≈ 2 km/px，显示 12 个城市」），但内部判据统一是屏幕像素。

**规则的两级配置**

| 级别 | 可设内容 |
|------|----------|
| **图层级**（默认，够用） | 该类对象的显示条件：`minScreenSize`（小于此尺寸不显示）、`maxScreenSize`（大于此尺寸不显示，用于「放大后小点让位给面」）；标签是否显示、标注字号是否随缩放衰减 |
| **对象级**（覆盖图层默认） | 单个对象的 `importance`（重要度 1~5）与 `alwaysVisible`；重要对象在小比例下优先保留 |

**默认预设（按类型给，用户可改）**

| 对象类型 | 小比例（看全图） | 中比例 | 大比例（贴近看） |
|----------|------------------|--------|------------------|
| 国界 / 势力范围（面） | 显示（细线） | 显示（正常） | 显示（带描边） |
| 国名 / 地区名（文字） | 显示 | 显示 | 显示 |
| 城市 / 据点（符号） | 仅重要度 ≥ 4 | 重要度 ≥ 2 | 全部 |
| 村落 / 细节符号 | 隐藏 | 仅重要度 ≥ 4 | 全部 |
| 注记文字 | 隐藏（< 11px 不可读） | 显示 | 显示 |

**实现要点**

- 判定是纯函数：`shouldRenderFeature(feature, zoom, layerRule) → boolean`，放在 `map-core`，**可单测**，与 Canvas 无关
- 渲染顺序：先按视口 + 包围盒拉取 → 再按显示规则过滤 → 最后绘制。过滤放在绘制前，**顺带降低小比例下的绘制量与内存**
- **标签避让列入二期**（诚实说明代价）：让标签互不重叠、靠引线连接，需要碰撞检测与优先级排版，工作量接近一个独立子项目；首期只做「按屏幕尺寸显隐」
- 与编辑的关系：显示规则只影响**显示**；被隐藏的对象仍可搜索、可编辑、可导出。导出时可选「按当前视图比例导出」或「导出全部对象」
- 面板落点：图层面板里每个图层多一个「显示范围」折叠区（滑杆 + 开关）；指针模式选中对象时，属性面板可覆盖 `importance` / `alwaysVisible`

### 10.4 渲染细节


- 索引 → 像素：预生成 `ImageData`，用 `Uint32Array` 视图写入（比逐像素 `putImageData` 快一个量级）
- **自由连续缩放**（适应窗口 ~ 32×）：按 §5.6.1 的区间切换图像平滑——`zoom < 1` 开平滑、`1 ≤ zoom < 8` 像素完美、`≥ 8` 可选平滑
- **经纬网**：每 30° 一条淡线（可关），它同时是「这是球面展开」的视觉提示
- DPR 适配沿用 `WorldGraphPage` 的既有模式（`dpr = min(devicePixelRatio, 2)` + `setTransform`）

## 11. 存储与配额

### 11.1 三类数据各归其位

| 数据 | 存哪 | 原因 |
|------|------|------|
| 白板元信息 / 图层 / 矢量对象 | D1 | 需要关系查询与增量更新 |
| 地形栅格瓦片 | D1 `map_tiles` | 按瓦片增量读写，D1 语义合适 |
| 上传底图（image 型地图） | KV | 现有实现不动 |
| 导出的成品 PNG | 首期仅本地下载 / 系统分享 | 省 KV 写额度 |
| 编辑中草稿 | 本地（IndexedDB / SQLite） | 本地优先，离线可画（多端必需） |

### 11.2 为什么服务端不碰图像

浏览器 / WebView 侧已有 Canvas 能力：导出时把白板渲染成 `Blob`，需要上传时直接 POST 字节流，Worker 只做**大小校验 + 写 KV + 返回 key**。Worker 不需要任何图像库。

> ⚠️ 服务端现有限制是**单文件 ≤ 8MB**（`routes/images.ts:24-29`，比文档里的 KV 25MB 更严格）。导出调优规则：① 优先 `image/png`；② 超 8MB 自动降级 `image/webp`（质量 0.9）；③ 仍超限则提示「按当前视口 / 降低白板档位导出」。

### 11.3 体积与额度测算（2048×1024 白板）

| 内容 | 未压缩 | gzip 后 | 说明 |
|------|--------|---------|------|
| 地形层（32 瓦片） | 2 MB | ≈ 30～150 KB | 大色块压缩比高 |
| 单个专题图层（矢量） | — | ≈ 10～200 KB | 取决于对象数量 |
| 5 个图层合计 | — | **≈ 100～500 KB / 张地图** | 含地形 + 4 个专题层 |

| 免费额度 | 本方案消耗 | 结论 |
|----------|-----------|------|
| D1 单库 500MB | 每张地图 ≈ 0.1～0.5 MB → 1000+ 张 | 早期够用 |
| D1 行写入 10 万 / 天 | 每次保存只写脏瓦片或单个对象 | 几乎无感 |
| KV 写入 1000 / 天 | 仅上传底图 / 导出图时写 | 不构成压力 |
| KV 读取 10 万 / 天 | 栅格与对象都不走 KV | 无影响 |

> 结论：**把栅格放 D1、把 KV 只留给位图**，是方案在免费额度内成立的关键。

### 11.4 保护措施

- 白板尺寸上限 16384×8192（仅桌面端，需强提示确认）；`8192` 以上档位默认禁用移动端
- 单瓦片解压后固定 256×256 = 64KB，服务端可据此硬校验，防畸形数据
- 单次保存请求体上限 2MB（超出提示「本次改动过大，请稍后再保存」）
- 图层数量上限 20，单图层矢量对象上限 2000（可调）
- 地图创建 / 保存 / 导出纳入 `quota.ts`（现状地图接口完全没有限额，需补）

## 12. 接口设计

> ⚠️ **本章描述的是「主站这个宿主」提供的 API，不是插件的 API。**
> 插件只认 `MapHostAdapter`（§15.3）；主站把下面这些接口实现成 `HttpMapHostAdapter`（`packages/map-editor-web`）交给插件即可。换句话说：**换一个宿主，本章整体作废，而插件一行不用改**——这正是插件化的意义。

全部挂在 `/api` 前缀下，沿用 `ok` / `fail` 封装与 `requireLogin` + `canEdit` 校验。

### 12.1 地图与白板

| 方法 | 路径 | 说明 |
|------|------|------|
| `POST` | `/api/worlds/:worldId/maps/canvas` | 新建白板 `{ name, width }`（`height = width / 2` 服务端算出并校验；自动建「地形」图层 + 默认调色板） |
| `GET` | `/api/maps/:mapId/canvas` | 元信息 `{ kind, projection, width, height, revision, radiusKm, palette, layers[] }` |
| `POST` | `/api/maps/:mapId/resize` | **白板改尺寸**：`{ revision, width, tiles: [...] }` 分批提交重采样后的瓦片；校验 2:1 与范围，成功则 `revision +1` 并清理旧瓦片（§5.6.2） |
| `PATCH` | `/api/maps/:mapId` | 已有接口扩展：改名 / 改调色板 |
| `DELETE` | `/api/maps/:mapId` | 已有接口扩展：级联删除图层、瓦片、对象，并**清理 KV 底图** |

### 12.2 图层

| 方法 | 路径 | 说明 |
|------|------|------|
| `POST` | `/api/maps/:mapId/layers` | 新增图层 `{ name, type }`（服务端按类型给默认 `storage` 与图例） |
| `PATCH` | `/api/maps/:mapId/layers/:layerId` | 改名 / 显隐 / 透明度 / 图例 |
| `PUT` | `/api/maps/:mapId/layers/order` | 批量提交排序 `{ layerIds: [...] }`（一次写多行） |
| `DELETE` | `/api/maps/:mapId/layers/:layerId` | 删除图层及其瓦片 / 对象（二次确认由前端负责） |

### 12.3 瓦片与对象

| 方法 | 路径 | 说明 |
|------|------|------|
| `GET` | `/api/maps/:mapId/tiles?rev=<revision>&layer=<id>&cols=0,1&rows=0,1` | 拉取瓦片（**必须带 `rev`**，见 §14.6） |
| `PUT` | `/api/maps/:mapId/tiles` | 保存脏瓦片 `{ revision, layerId, tiles: [{ col, row, data }] }` |
| `GET` | `/api/maps/:mapId/features?layer=<id>&bbox=...` | 按图层与视口包围盒拉取对象（分页） |
| `POST` / `PATCH` / `DELETE` | `/api/maps/:mapId/features[/:featureId]` | 矢量对象增删改（单对象粒度，天然增量） |

### 12.4 冲突处理

```
PUT /tiles 或 /features 的 body.revision !== 当前 revision
  → 409 + 当前 revision
  → 前端提示「这张地图已在别处被修改」→ 用户选择 [覆盖] 或 [放弃本地改动]
```

不做合并，但保留 revision 校验，防止「多标签页 / 电脑与手机同时打开」时静默覆盖——**这一条在多端场景下尤其重要**。

**权限**：创建、保存、图层与对象编辑需要 `canEdit`（与世界编辑权限一致）；读取需要 `canRead`。不引入新的权限模型。

### 13.5 性能验收标准

| 指标 | 目标 |
|------|------|
| 2048 白板首次打开 | ≤ 1.5s 可绘制（按可见视野懒加载瓦片） |
| 涂抹帧率 | ≥ 50fps（只重绘脏瓦片） |
| 视图缩放 / 平移 | 拖拽与滚轮 60fps（视野内瓦片重绘），缩放不产生网络请求 |
| 白板改尺寸 | 2048 → 4096 ≤ 3s；4096 → 2048 ≤ 4s（含分批上传） |
| 单笔撤销 | 即时（差异块，不重算全图） |
| 保存一次改动 | ≤ 300ms、请求体 ≤ 100KB |
| 切换 2D ↔ 3D | ≤ 500ms（纹理复用已有瓦片，不重新解码全部） |
| 尺度读数的刷新 | 指针移动时信息条与比例尺条实时更新（跟随 60fps 帧），**不得因换算阻塞绘制** |
| 面积统计 | 增量维护，落笔 O(覆盖范围)；「重新统计」全图扫描 ≤ 500ms（2048 白板） |
| 内存占用 | 白板栅格 + 瓦片缓存 ≤ 白板单层大小的 3 倍 |

### 13.6 与既有前端设施的衔接

| 既有事实 | 处理 |
|----------|------|
| `api()` 的 GET 有 10 秒缓存 + 并发合并 | 瓦片与对象拉取**必须把 `revision` 放进 URL**，否则撤销 / 重开后可能拿到旧数据 |
| 无状态库，`toast.ts` 是唯一模块级 store 先例 | 瓦片缓存与图层状态放模块级对象，避免 React 重渲染拖慢涂抹 |
| `WorldGraphPage` 已有 Canvas 先例（DPR + raf + `touch-action`） | 直接沿用 |
| 全仓无下载工具、无自研 undo/redo | 需自建 `downloadBlob()`（多端走能力适配，§14.5）与 `history.ts` |
| 写操作后习惯「重新拉全量」，无乐观更新 | 标记增删改沿用该习惯；**瓦片与对象保存依赖本地最新状态，不重新拉取** |
| 地图类型散落在 `MapsPage.tsx` 局部 interface | 提到 `packages/map-core/src/types.ts`（插件对外类型必须自持，不能依赖主站） |

## 14. 3D 地球仪（需求 2）

### 14.1 技术选型与体积

| 方案 | 体积 | 说明 |
|------|------|------|
| **裸 WebGL2 + 自写着色器**（推荐首期） | ≈ 0（无新依赖） | 球体 = 一个 UV 球网格 + 纹理采样；本方案只需贴图与旋转，无需 3D 引擎 |
| Three.js | ≈ 150KB（gzip） | 生态好、后续要加光照 / 大气 / 星空更省事，但需按需引入与懒加载 |

**首期用裸 WebGL2**：即便加上大气辉光、星空与昼夜明暗（§14.3），自写球体 + 菲涅尔 + 程序化星空 + 黄昏线的着色器总量仍在 300 行左右，零新依赖；而引入 Three.js 需要额外的加载与分包配置，而本仓库 `vite.config.ts` 目前没有任何 `manualChunks` / 体积阈值设置。

### 14.2 实现要点

| 环节 | 做法 |
|------|------|
| 纹理 | 直接使用白板合成图（等距圆柱 = 标准球面 UV 贴图，无需重投影） |
| 分层 | 每个可见图层合成到一张离屏纹理（含透明度），一次上传；图层变化时只重做受影响的部分 |
| 球体 | 经纬网格细分（如 128×64），UV 从顶点位置推导 |
| 相机 | 球外观测：`theta`（经度）/ `phi`（纬度）/ `distance`（距离）三参数，鼠标拖拽旋转、滚轮缩放 |
| 拾取 | 屏幕射线与球面求交 → `sphereToLonLat` 得经纬度（为 Phase 3「在球上放标记」预留） |
| 标记 | 标记点的球面坐标由经纬度实时计算，投影到屏幕后以 2D 叠加层绘制（比在 3D 里做精灵更简单、更清晰） |
| 经纬网 | 在着色器里按经纬度画网格线（`fract(uv * n)` 步进），复用 2D 的网格开关 |
| 截图 | `canvas.toBlob()` 复用同一套导出与下载能力 |

### 14.3 美术效果：大气辉光 + 星空背景 + 昼夜明暗（已定案）

三项都做，并且**全部用自写着色器实现**——加进来后总量仍在 300 行左右着色器源码内，比引入 Three.js（≈150KB）更省，也更符合仓库现状（无分包配置，不宜盲目上大包）。

#### 14.3.1 大气辉光

| 项 | 做法 |
|----|------|
| 原理 | **菲涅尔效应**：视线越接近切线方向穿过的大气越厚 → 边缘发亮、正对圆心处透明 |
| 实现 | 半径略大的第二个球（外扩约 1.03R），背面渲染，`intensity = pow(1 - dot(N, V), power)` |
| 参数 | 辉光颜色（默认取主题 `accent` 冷化后的青蓝）、强度、扩散指数 |
| 代价 | 一次额外球体绘制，可忽略 |

#### 14.3.2 星空背景

| 项 | 做法 |
|----|------|
| 原理 | **程序化生成，不用图片资源**：全屏片元着色器用哈希噪声撒星点（`stableHash(floor(uv * 密度))`），同一位置恒星固定不动 |
| 参数 | 密度、大小、亮度、是否闪烁（**默认关闭闪烁**，与「档案馆 / 编年史」的沉静气质一致，不做游戏化闪烁） |
| 底色 | 深墨蓝（如 `#070c14`），与编辑器主背景同族，不突兀 |
| 代价 | 一次全屏四边形绘制，`gl_FragColor` 里几次 `fract/sin` 运算 |

#### 14.3.3 昼夜明暗（黄昏线）

| 项 | 做法 |
|----|------|
| 原理 | 由**太阳方向**决定：`L = normalize(sunDir)`（世界空间），`lambert = dot(N, L)`，用 `smoothstep(-0.1, 0.1, lambert)` 得到昼夜过渡带 |
| 昼面 | 星球本色（保持地图可读性，**不做强烈高光**） |
| 夜面 | 压暗至约 25% + 偏深蓝（`mix` 向 `#0a1420`） |
| 夜间灯光（可选，默认关） | 按「已画陆地」的掩膜在夜面加暖黄噪点，需要一份额外的陆地掩膜纹理；**默认关闭**，单独开关与强度滑杆 |
| 太阳方向 | **不是真实天文计算**，而是「太阳直射点」的用户设定：经度滑杆（0~360°）+ 纬度（默认 0°）。拖经度滑杆可把黄昏线移到想看的位置，**只需更新一个 uniform，不必每秒重渲染** |

#### 14.3.4 性能档位（美术效果必须能降级）

| 档位 | 效果 | 默认给谁 |
|------|------|----------|
| 完整 | 星空 + 大气辉光 + 昼夜（dpr 上限 2） | **桌面端默认** |
| 精简 | 星空 + 昼夜，**关闭大气辉光**（dpr 上限 1.5） | **移动端默认** |
| 最简 | 关闭全部美术效果，仅贴图 + 经纬网 | 低端设备 / 首帧探测不达标 |

**已定案：桌面默认「完整」、移动端默认「精简」，但手机用户可以自己打开大气辉光。**

- 判定"移动端"的口径：触摸为主（`PointerEvent` 粗指针）**或**短边 ≤ 768px —— 与主站现有断点一致
- 三项效果各有独立开关（`features.globe3d: { atmosphere, stars, dayNight }`），用户可以「要星空不要昼夜」，也可以「只要大气辉光」
- **入口在 3D 视图的「显示设置」里**（右上角齿轮）：档位三选一 + 三个效果开关 + 一个「恢复默认」；移动端打开时先在设置面板里给一句原因说明（「手机默认关闭大气辉光以保证流畅」），而不是弹窗打断
- 用户手动选择**优先于自动判定**：手动开「完整」后不再被自动降档；若首帧耗时仍超标，只给一句非阻断提示（「当前设置可能影响流畅度，可切回精简」），**不擅自改回去**
- 偏好按**设备**记（本地存储，与主站既有 `toast.ts` 的轻量本地偏好同类，不进地图数据、不进快照——因为它是"这台设备"的属性而不是地图的属性）
- 自动降档的触发条件：屏幕尺寸、`devicePixelRatio`、`deviceMemory`（可用时）、**首帧渲染耗时**（超阈值降一档并提示）
- 关闭全部效果后 **3D 仍然完全可用**：旋转、缩放、拾取、截图都不受影响（§14.5 的降级原则）

#### 14.3.5 与插件主题的一致性

- 所有颜色都走 `MapEditorTheme` 扩展项（如 `globeSkyColor` / `globeAtmosphereColor` / `globeNightColor`），宿主不传则用默认值 —— 换项目时观感仍然统一
- 默认配色刻意克制：**深墨蓝星空 + 冷青蓝辉光 + 柔和黄昏过渡**，避免「宇宙炫彩壁纸」式的观感，与项目既定的「档案馆、编年史」气质一致

### 14.4 2D 与 3D 数据一致性（需求 2 的一部分）

- **不产生第二份数据**：3D 只读白板 + 图层 + 对象，任何绘制都回到 2D 完成
- 切换时保留视野锚点：把 2D 视口中心换算成经纬度，3D 相机自动朝向该点；反向亦然
- 首期 3D 不显示标记的编辑手柄，点击标记只做「查看关联条目」（与 2D 指针模式一致）
- **美术效果（§14.3）只属于 3D 视图**：2D 永远保持「绘图台」的平实观感（这是编辑视图，不是展示视图），这样「好看」与「好用」不互相牵制
- **昼夜明暗只影响视觉，不影响数据**：夜面压暗不会改变任何瓦片、对象或统计；截图导出时可选择「带昼夜效果」或「均匀光照」

### 14.5 降级策略（关键：不能出现「应用里有、网站里没有」）

| 情况 | 表现 |
|------|------|
| 支持 WebGL2 | 正常 3D（含美术效果，按 §14.3.4 档位） |
| 不支持 WebGL2（老设备 / 某些 WebView） | 顶部提示「当前设备不支持 3D 地球仪」→ 自动停在 2D；**功能入口保留但禁用**，并给出原因 |
| 显存紧张（8192 白板纹理过大） | 自动降低合成纹理分辨率（如 4096×2048）与提示 |
| 首帧渲染过慢 / 低端移动设备 | 自动降一档美术效果（完整 → 精简 → 最简）并提示可手动调整 |

> 原则：**数据层面零损失，表现层面可降级**。3D 与美术效果不可用与否，都不影响任何编辑、保存、导出与图层能力。

## 15. 插件化与独立分发（需求 6）

> 需求 6：**地图编辑器要能从主站独立出来**，做成一个「小插件」——可单独升级，也可安装到其他项目上复用。
> 现状：`packages/storage`、`packages/sync`、`apps/desktop`、`apps/android` **全部尚未创建**，因此本节不是「检查现状」，而是**必须在写第一行编辑器代码之前就确立的架构约束**——否则耦合一旦长成，抽离成本会高到只能重写。

### 15.1 插件化的核心：宿主可控，插件不假设

一句话原则：**插件不假设宿主是什么**——不假设后端是 D1、不假设路由是 React Router、不假设主题色、不假设有登录体系、不假设跑在网站上。

由此推出四条硬约束：

| # | 约束 | 检查方式 |
|---|------|----------|
| 1 | 插件包**不 import 主站任何模块**（含 `@create-world/core`、`src/lib/api`、`src/components/*`） | CI 中一条 grep 规则即可守住 |
| 2 | 插件包**不出现宿主概念**：无 D1 / 世界 / 条目 / 邀请码等业务词 | review 时看命名与类型 |
| 3 | 插件包**不直接 fetch**：所有数据进出走宿主实现的 `MapHostAdapter` | 同理 |
| 4 | **UI 层不依赖 React Context、不读写全局单例**：`<MapEditor>` 所需的一切都从 props 传入 | grep `createContext` / `useContext`；这条是 §15.6.1「将来能补 Web Component」的前提——有 Context 就没法包成任意框架可用的标签 |

> 约束 4 现在看起来"没必要"（首期只有主站一个宿主），但它是最便宜的那份保险：等真有非 React 项目要接入时，补一层薄壳即可，而不是回头重写状态流。

### 15.2 包拆分

**已定案：包名用中性命名 `@worldmap/*`，与主站的 `@create-world/*` 明确切开；首期只在仓库内用（`"private": true`，不发布 npm）。**

|------|------|----------|
| `packages/map-core` | `@worldmap/core` | 纯逻辑内核，零运行时依赖 |
| `packages/map-editor` | `@worldmap/editor` | React 组件（peerDep 声明 React） |
| `packages/map-editor-web` | `@worldmap/editor-web` | 浏览器侧适配实现（可选装） |
| `packages/map-element`（预留） | `@worldmap/element` | Web Component 壳，首期不建（§15.6.1） |

### 15.3 对外 API（插件与宿主之间唯一的契约）

```tsx
/** 宿主必须实现的适配器：插件与外界的所有数据进出都走这里 */
interface MapHostAdapter {
  /** 读取地图元信息（白板尺寸、天体半径、图层列表、revision） */
  loadMeta(mapId: string): Promise<MapMeta>;
  /** 读取指定瓦片；不存在的瓦片返回 null */
  loadTiles(mapId: string, layerId: string, coords: TileCoord[]): Promise<(Tile | null)[]>;
  /** 增量写入变化瓦片；revision 不匹配时应返回冲突 */
  saveTiles(input: {
    mapId: string;
    layerId: string;
    tiles: Tile[];
    revision: number;
  }): Promise<{ revision: number; conflict?: boolean }>;
  /** 按视口读取矢量对象 */
  loadFeatures(mapId: string, query: FeatureQuery): Promise<MapFeature[]>;
  /** 矢量对象写操作 */
  saveFeatures(input: { mapId: string; upsert: MapFeature[]; removeIds: string[] }): Promise<void>;
  /** 图层增删改（含排序） */
  saveLayers(mapId: string, layers: MapLayer[]): Promise<void>;

  /** 可选：把已画统计交给宿主持久化（宿主不实现则插件本地统计，见 §7.6） */
  saveStats?(mapId: string, stats: MapScaleStats): Promise<void>;
  /** 可选：本地草稿与恢复（宿主不实现则退化为仅内存，离开页面即丢） */
  drafts?: DraftStore;
}

/** 组件 props */
interface MapEditorProps {
  mapId: string;
  adapter: MapHostAdapter;
  /** 只读模式（公开世界、分享页、只读嵌入） */
  readOnly?: boolean;
  /** 初始视图：经纬度中心 + 缩放 */
  initialView?: { lon: number; lat: number; zoom: number };
  /** 主题；不传则用内置深色默认值（§15.4） */
  theme?: MapEditorTheme;
  /** 界面语言；默认 zh-CN */
  locale?: "zh-CN" | "en";
  /** 显示哪些面板与工具；不传则全开 */
  features?: { layers?: boolean; scale?: boolean; measure?: boolean; globe3d?: boolean; export?: boolean };
  /** 事件回调（插件不自己弹宿主样式的提示，除非宿主不接管） */
  onSaveStateChange?: (state: "idle" | "saving" | "saved" | "offline" | "error") => void;
  onDirtyChange?: (dirty: boolean) => void;
  onExport?: (blob: Blob, suggestedName: string) => void | Promise<void>;
  onMarkerClick?: (markerId: string, entryRef?: string) => void;
  onError?: (error: MapEditorError) => void;
}

/** 命令式 API：通过 ref 调用 */
interface MapEditorHandle {
  save(): Promise<void>;
  exportImage(options?: { scale?: number; includeScaleBar?: boolean; includeGraticule?: boolean }): Promise<Blob>;
  getSnapshot(): Promise<MapEditorSnapshot>;   // 完整可移植快照（§15.7）
  loadSnapshot(snapshot: MapEditorSnapshot): Promise<void>;
  fitToWorld(): void;
  setLayerVisibility(layerId: string, visible: boolean): void;
}
```

**设计的取舍**：把 `adapter` 做成必需参数而不是可选——因为「插件自带后端」是伪需求，插件的价值恰恰在于**不绑定后端**。宿主给什么存储，它就用什么存储。

### 15.4 主题与样式隔离

插件**不假设宿主的 CSS 变量名**（主站的 `--bg-soft / --accent` 只是它自己的事）。做法是：插件用**自己命名空间**的主题 token，宿主可通过 `theme` 覆盖，未传则回退到内置默认。

```ts
interface MapEditorTheme {
  background: string;      // 编辑器底
  panel: string;           // 面板 / 工具栏
  border: string;
  text: string; textDim: string; textFaint: string;
  accent: string;          // 选中态、笔刷光标
  radius: string;          // 圆角
  fontSans: string; fontSerif: string;
}
```

- 内部样式用 CSS Modules / 局部类名 + 自建前缀，**不污染宿主全局样式**
- 主站接入时把 `:root` 的变量映射进来即可，观感与现有页面一致；其他项目接入时给一套自己的配色
- 主站当前只有深色主题（`styles.css:2-17`），插件默认色板与之取同值，保证「装进主站像原生」

### 15.5 可插拔的三层能力（按宿主能力递进）

| 宿主提供了什么 | 插件可用能力 | 说明 |
|----------------|--------------|------|
| 只给 `loadMeta / loadTiles / saveTiles` | 2D 绘制 + 图层 + 撤销 + 比例尺 | **最小接入**，10 分钟能接上 |
| 再给 `loadFeatures / saveFeatures` | 加矢量对象图层 | 专题图层需要 |
| 再给 `drafts` / `saveStats` / `onExport` | 加草稿恢复、统计持久化、导出落图 | 完整体验 |

> 这条「能力递进」是插件可复用的关键：**宿主不必一次实现全部接口**，缺什么就少什么能力，而不是启动失败。可选成员一律用 `?` 标注。

### 15.6 分发的三种形态

| 形态 | 适用场景 | 优点 | 代价 |
|------|----------|------|------|
| **npm 包**（`@worldmap/editor`） | React 项目、可控构建 | 类型完整、可 tree-shaking、可只引 2D 不引 3D、props 与回调就是普通函数 | 宿主必须是 React（或 React 兼容的包装层） |
| **Web Component**（`<map-editor>`） | 任何前端框架 / 纯 HTML 嵌入 | 框架无关，一行标签即可用；Shadow DOM 天然样式隔离 | 属性只能字符串 / JSON，回调要走 `addEventListener`；内部仍要打包一份 React（见下） |
| **iframe 嵌入页** | 完全隔离、第三方站点 | 零冲突、可独立部署与升级 | 通信只能 postMessage，能力最受限 |

**首期做 npm 包**（也是本仓库现在就需要的东西），Web Component 作为第二个可选出口，iframe 暂不做。

#### 15.6.1 Web Component 到底是什么、什么时候值得补

**它是什么**：浏览器原生标准，本质是「自定义 HTML 标签 + 影子 DOM（Shadow DOM）+ 生命周期回调」。使用者不需要装任何框架：

```html
<script type="module" src="https://cdn.example.com/map-editor.js"></script>
<map-editor map-id="abc" theme="dark"></map-editor>
```

对比现在的 npm 包用法：

```tsx
<MapEditor mapId="abc" adapter={myAdapter} theme={myTheme} onSaveStateChange={...} />
```

**优点**

| 优点 | 说明 |
|------|------|
| **框架无关** | Vue / Svelte / Angular / 纯 HTML / WordPress 后台 / 旧 jQuery 项目都能直接嵌，不需要对方懂 React |
| **零构建接入** | 一句 `<script>` + 一个标签就能跑，对「想把地图编辑器塞进某个后台系统」的场景最省事 |
| **样式天然隔离** | Shadow DOM 把内部 CSS 关在组件里，既不污染宿主也不被宿主污染——比 §15.4 的命名空间做法更彻底 |
| **`<script>` + CDN 即可用** | 不需要 npm 安装、打包器、类型配置 |

**代价（真实成本，不要低估）**

| 代价 | 说明 |
|------|------|
| **配置传递先天受限** | HTML 属性只能传字符串；传对象 / 函数只能走 JS 属性赋值或 `addEventListener`。React 宿主还需注意：React 19 之前不支持给自定义元素传属性，得手写 wrapper 用 `ref` 设值、手动 `addEventListener` |
| **内部仍要打包一份 React** | 组件内部还是用现有的 React `MapEditor` 渲染，于是宿主如果是 React 应用，页面上就存在**两份 React**（体积增加，且要避免两套调度互相干扰）。用 Preact 等轻量替代可缓解，但那要另写适配层 |
| **事件要比 props 麻烦一档** | 现有 `onSaveStateChange` 这类回调要重新映射成 `CustomEvent`（`detail` 里带数据），使用方得多写 `addEventListener` + `event.detail` 解包 |
| **样式定制能力变弱** | 主题只能通过 CSS 变量 + `::part()` 暴露，控制力弱于直接传 `theme` 对象 |
| **Shadow DOM 的连带问题** | 字体继承（主站用思源宋体，需显式注入或 `::part` 透出）、全局快捷键（编辑器抢键盘要处理焦点边界）、无障碍语义需要额外处理（label、焦点环、屏幕阅读器） |
| **维护两条对外 API** | npm 的 props API 与 WC 的属性 / 事件 API 要同步演进，每个新功能可能要多写一份映射与文档 |

**结论：首期不做，但把地基留足。**

| 现在做 | 将来触发条件（满足任一即可补 WC，成本约 1~2 天） |
|--------|--------------------------------------------------|
| 只发 npm 包；但**内核与外观彻底分离**（`map-core` 纯逻辑、`map-editor` 只认 `MapHostAdapter` / `theme` / `locale`），**不依赖 React Context、不做全局单例** | ① 有非 React 的项目要接入；② 想做成「嵌入任意后台系统」的形态；③ 想上架插件市场、或对外提供 CDN 版本 |

> 关键点：**Web Component 那层壳的难度取决于内部分层，而不是壳本身**。只要 `map-editor` 的输入全部走 props（不依赖 React Context、不读写全局变量），补 WC 就是一层几十行的薄壳；反之，如果内部散落着 Context 和全局状态，壳再薄也包不干净。所以 §15.1 那三条硬约束才是真正的准备工作。

**推荐优先级**：npm 包（首期）→ Web Component（有外部接入需求时）→ iframe（需要给完全不受控的第三方站点用时）。

### 15.7 数据可移植性：导出 / 导入一份完整快照

要让插件能「装到别的项目上」，数据必须能跟着走，所以提供与后端无关的快照格式：

```ts
interface MapEditorSnapshot {
  format: "map-editor-snapshot";
  version: 1;
  board: BoardSpec;                    // 尺寸 + 投影 + 天体半径
  palette: TerrainBrush[];
  layers: MapLayer[];
  tiles: { layerId: string; col: number; row: number; dataBase64: string }[];
  features: MapFeature[];
  stats?: MapScaleStats;
}
```

- 一次 `getSnapshot()` 就能把整张地图取成**一个自包含 JSON**（瓦片以 base64 内嵌），存文件、换后端、迁移项目都不丢东西
- 服务端（主站）的导入导出沿用同一格式，避免出现两套序列化
- 与 `docs/方案.md` 第 12 章的导出格式**保持兼容**：世界备份 JSON 里的 `maps` 字段将来直接放这个快照

### 15.8 版本、升级与联调

| 关注点 | 做法 |
|--------|------|
| 版本线 | 插件独立发版（`@worldmap/editor@0.x` → 稳定后 `1.0`），**不跟随主站版本**；升级插件不必动主站 |
| 发布位置 | **首期只在仓库内用**：三个包均为 `"private": true`，仅通过 pnpm workspace 引用；不发布公共 npm、暂不注册 npm scope。待接口稳定且有外部需求时再决定是否发布与如何托管 |
| 破坏性变更 | 插件 API 变更遵循 semver；`0.x` 阶段允许小步快跑但每次在 `docs/更新日志.md` 登记 |
| 数据兼容 | 快照与落库格式带 `version`，插件负责向前兼容读取旧版本（§15.7、`cwt1` 的压缩标识位同理） |
| 宿主兼容声明 | `package.json` 里声明 `peerDependencies: { react: ">=18" }`，避免宿主 React 版本冲突 |
| 仓库策略 | **一期先放在主仓库的 `packages/` 内**（单一工作区、改动最小、便于同步），但严格保持零耦合；接口稳定后可整体抽到独立仓库，主站改为引用 |
| 边界守护 | CI 检查插件包内**不得出现** `@create-world/*`、`/api/`、`window.location`、业务词（world / entry / invite）、**React Context（`createContext` / `useContext`）**。这条规则比任何口头约定都可靠，也直接决定了将来补 Web Component 的成本 |

### 15.9 与多端一致性的关系（需求 4 的落地）

插件化天然解决了多端问题：**Tauri / Capacitor 需要做的只是换一个 `MapHostAdapter` 实现**（SQLite 版），编辑器组件与全部逻辑零改动。

| 端 | adapter 实现 | 平台能力 |
|----|--------------|----------|
| Web（主站） | `HttpMapHostAdapter`（走 `/api`）+ IndexedDB 草稿 | `CompressionStream` / `<a download>` / WebGL2 |
| Desktop（Tauri） | `SqliteMapHostAdapter` | 内置压缩 / 系统保存对话框 / WebGL2 |
| Android（Capacitor） | `SqliteMapHostAdapter` | 内置压缩 / 系统分享 / WebGL2 |

> 判据（同 §15.1）：**做桌面版时如果需要改编辑器组件代码，说明插件化没做干净。**

### 15.10 决策：现在建包，暂不拆仓库

| 选项 | 评价 |
|------|------|
| A. 主仓库内建 `packages/map-core` + `packages/map-editor`（**选用**） | 改动最小、单一 pnpm 工作区、主站与插件可一起改一起测；零耦合靠 CI 四条规则守住 |
| B. 立刻拆成两个 git 仓库 | 边界最干净，但联调时要 `yalc` / `file:` 链接，且 `map-core` 与 `map-editor` 会**同步演进**（比例尺、投影都会变），双仓库徒增摩擦 |

选 A 的理由：**真正的独立性来自「零耦合 + 类型契约 + 独立版本号」，不是来自目录在哪个仓库**。等接口稳定（约 1.0）需要给外部项目用时，再把 `packages/map-*` 整体搬出去，主站从 npm 装——届时搬家是纯机械操作。

**已定案（配套决定）**：`map-element`（Web Component 壳）**首期不建**，但 §15.1 的四条硬约束先做实——将来要补，是一层几十行的薄壳，而不是重写状态流（理由与触发条件见 §15.6.1）。

### 15.11 给插件的技术选型约束（为了可复用，不是为了现在）

| 约束 | 理由 |
|------|------|
| `map-core` **零运行时依赖** | 谁都能装；也保证它能在任何 JS 环境（含 Worker）里跑 |
| React 只出现在 `map-editor` 的 `peerDependencies` | 不给宿主塞第二份 React |
| 3D 地球仪**懒加载 + 可关闭** | 不用 3D 的项目不该背 WebGL 代码与包体积 |
| 不引 fabric / konva / three | 与仓库既有极简依赖现状一致（现依赖只有 leaflet、d3-force、TipTap、React） |
| 不写死中文以外的文案 | 首期 zh-CN + 预留 `locale`；文案集中在 `map-editor/locales/`，不散落 |
| 不假设深色主题 | 主题全走 token（§15.4） |

### 15.12 压缩能力抽象（跨端最容易踩的兼容坑）

`cwt1` 需要 gzip，而 `CompressionStream` 在旧版 WebView（尤其安卓低版本）可能缺失。因此：

- `cwt1` 编解码写在 `map-core`，**压缩器由调用方注入**（`encodeTile(indices, compress?)`）
- 格式里的压缩标识位（`0` 原始 / `1` gzip）让解码端不依赖具体压缩器
- 某端没有原生压缩 → 退化存原始字节（体积换功能可用），或该端自带轻量 deflate
- **绝不允许**「网站存的瓦片应用解不开」：编解码器只有一份，且在零依赖的 `map-core` 里

### 15.13 素材目录（纹理 / 图标 / 3D 贴图）

素材放在**插件包内**：`packages/map-editor/assets/`。理由与前一条（压缩器注入）同源——
插件要能独立安装到别的项目，素材必须跟着包走，不能散落在主站的 `public/` 里。

| 目录 | 内容 | 何时用得上 |
|------|------|-----------|
| `terrain/tiles/` | 地形填充图案（**四边无缝平铺**，2 的幂尺寸） | 二期「地形纹理」；现在的七种图案是程序化生成的 |
| `terrain/paper/` | 纸张纤维 / 污渍 / 做旧质感 | 已在用（`terrain-render.ts` 程序化生成，暂无文件） |
| `terrain/edges/` | 地形边界的花边与笔触 | 二期 |
| `ui/` | 工具栏与图层面板图标（SVG，`viewBox="0 0 24 24"`，用 `currentColor`） | 现在用文字标签，换图标时 |
| `globe/` | 星空背景、大气辉光、夜面灯光掩膜 | Phase 1 第 15 项（3D 地球仪） |
| `fonts/` | 自带字体（**必须可商用**，附同名 `LICENSE`） | 需要统一手绘地图字风时 |

三条硬规矩：

1. **能程序化生成就不落地成文件**：图案要能随调色板变色、随缩放平铺，写死一张 PNG 就丧失了这两种能力，
   还平白多几十 KB。文件形态只留给「画不出来 / 画得慢」的素材（星空、辉光、复杂笔触）。
2. **插件本体不请求素材**（CI 边界规则第 3 条）：素材被构建进包，或由宿主以 URL 注入，插件内不出现 `fetch`。
3. **加载失败必须能降级**：纹理缺失时退回纯色填充，不能让编辑器白屏。

登记规则、命名与规格约定见 `packages/map-editor/assets/README.md`（含素材清单表：
每加一份素材就登记一行来源与许可证，来源不明的一律不收）。

> **主站自己的素材不放这里**：Logo、界面插图、演示与测试用的底图放仓库根目录 `assets/`，
> 职责划分见 `docs/方案.md` §11.1「素材库的分工」。判断方法：这份素材换个项目还能不能用。

- **产品**：**自由输入宽度 3000（自动规整为 3072×1536）** 新建白板 → 视图缩放在适应窗口 ~ 32× 之间自由缩放且光标锚点不漂移、`zoom < 1` 与 `≥ 1` 的采样切换生效 → 涂出海洋与大陆 → 新增「政治」「军事」两个图层并调顺序 / 透明度 / 显隐 → 放 3 个标记并关联条目 → 保存 → 刷新后完全一致 → **把白板从 3072 无损放大到 6144 再缩回 3072，内容与矢量对象完全一致（×2 往返零损失）** → 切 3D 旋转查看并截图 → 导出 PNG；全程信息条显示每像素实距与变形倍率、比例尺随纬度实时变化、涂完大陆后立刻看到面积与真实世界对照；全流程在手机上同样可完成（3D 视设备能力）；§7.9 的 12 项尺度验收全部通过- **比例尺显示规则（需求 7，可测）**：① 在「政治」图层接入 100 个城市符号，缩到全图时只剩重要度 ≥ 4 的若干；② 放大到贴近时 100 个全部出现；③ 把某城市设为 `alwaysVisible` 后，全图下它依然显示；④ 隐藏的对象仍能被选中编辑（说明只是显示规则，不是数据删除）
- **3D 美术（需求 8，可测）**：① 三档性能档位切换后帧率有明显差异且画面可辨认；② 关闭「星空 / 大气 / 昼夜」中任意一项都不影响旋转、缩放、拾取与截图；③ 拖动太阳经度滑杆时黄昏线随之移动且帧率不掉；④ 截图导出可选「带昼夜效果」与「均匀光照」两种；⑤ **手机上默认无大气辉光，从显示设置打开后立刻生效，且刷新页面后仍保持该选择**
- **插件化（需求 6）**：① CI 四条边界检查通过（无 `@create-world/*`、无 `/api/`、无业务词、**无 React Context**）；② 用一个**与本仓库无关的最小宿主**（几十行 HTML + 一个内存适配器）把 `<MapEditor>` 跑起来并完成绘制 + 保存 + 导出，证明它不依赖主站；③ 主站页面文件在 50 行以内（只做适配器注入）；④ **内核与外观的可分离性抽查**：把 `MapEditor` 的 props 原样搬到一张空白测试页即可运行，无需任何额外环境准备
- **性能**：2048 → 4096 改尺寸 ≤ 3s、4096 → 2048 ≤ 4s；32× 放大下涂抹仍 ≥ 50fps（§13.5）；3D 完整档位在桌面 ≥ 50fps、移动端精简档 ≥ 30fps；`shouldRenderFeature` 过滤 1 万个对象的耗时 ≤ 5ms

## 17. 风险与对策

| 风险 | 影响 | 对策 |
|------|------|------|
| 白板栅格撑爆 D1 500MB | 后期无法写入 | 默认宽度 2048、空瓦片不落库、图层与地图数量限额；接近上限时提供「瓦片迁移到 KV / R2」预留开关（存储适配层已在总方案设计中） |
| 用户把白板改到 16384 导致体积/内存爆炸 | 应用卡死、额度被吃 | 上限校验 + 强提示 + 桌面端限制 + 改尺寸前显示预计体积；移动端不给超大档 |
| 高纬变形导致观感差 | 用户困惑 | 明确文档与界面提示；提供 3D 视图作为直观说明；不做极区投影 |
| 经度环绕未处理干净 | 接缝出现缺口 / 国界横穿全图 | 落笔双写、折线断段、包围盒双区间三处都必须实现并单测（§6.3） |
| 图层写死枚举导致不够用 | 需求 3 不达标 | `type` 开放 + 用户自定义图层 + 类型仅是预设模板（§9.1） |
| 跨端 / 插件分层被破坏（逻辑写进页面、插件 import 主站） | 应用版要重做一遍，「独立出去」变成重写 | 三条硬约束 + CI 边界检查 + 最小宿主冒烟测试（§15.1、§15.8） |
| 3D 引入大依赖 | 包体积膨胀 | 首期裸 WebGL2，零依赖（含大气 / 星空 / 昼夜着色器）；确需 Three.js 时懒加载并配 `manualChunks` |
| 3D 美术效果拖垮低端设备 | 移动端卡顿、耗电 | 三档性能档位（桌面默认完整 / 移动端默认精简，§14.3.4）+ 首帧耗时探测自动降级 + 三项独立开关；**用户手动开的档位不被擅自改回**；关闭全部效果后 3D 仍完全可用 |
| 显示规则让用户「找不到刚画的东西」 | 困惑与不信任 | 隐藏只是显示规则：对象仍可搜索 / 编辑 / 导出；面板显示「当前缩放下隐藏了 N 个对象」并给一键「显示全部」；对象可设 `alwaysVisible` |
| 标签避让被低估 | 二期严重超期 | 明确列为独立子项目、不进首期（§10.3）；首期只用屏幕像素显隐，不做自动排版 |
| 旧 WebView 缺 `CompressionStream` | 应用端打不开瓦片 | 压缩器注入 + 压缩标识位 + 退化存原始字节（§14.3） |
| 导出图超服务端 8MB 上限 | 无法保存到平台 | 自动降级 WebP → 仍超限则提示按视口 / 降档导出（§12.2） |
| 撤销栈内存增长 | 长时编辑变卡 | 差异块 + 30 步上限 + 边界矩形 |
| 涂大区域单次保存过大 | 保存失败 | 脏瓦片上限 32 + 分批提交 + 进度提示 |
| 尺度换算产生错误结论（用户照着错误数字改图） | 比没有比例尺更糟 | 用 haversine 而非像素直线、面积按纬度带加权、极区给变形倍率提示；§7.9 的 8 项数值验收必须全部通过 |
| 面积统计与真实数据不一致（增量计数漂移） | 用户失去信任 | 客户端增量 + 服务端权威副本 + 哈希差异校正 + 提供「重新统计」修复入口 |
| 尺度提示过于聒噪 | 干扰创作 | 一律非阻断式；三档预设 + 逐条阈值可调 + 可整体关闭（§7.7.1），且「知道了」可静音 30 天 |
| 插件与主站耦合（图省事直接 import 主站模块） | 「独立出去」变成重写 | 三条硬约束 + CI grep 检查 + 最小宿主冒烟测试（§15.1、§15.8、Phase 1 验收②） |
| 插件 API 过早定死，后续升级要破坏宿主 | 其他项目升级成本高 | `0.x` 阶段小步快跑、每次登记；`1.0` 后严格 semver；能力一律可选 + 版本化快照（§15.8） |
| 主站业务需求倒逼插件特化（如塞入条目 / 世界概念） | 插件失去通用性 | 宿主概念只允许出现在适配器实现里；插件侧只用 `mapId` / `markerId` 等中性标识（§15.1） |
| 自研 Canvas + WebGL 工作量大 | 延期 | Phase 1 拆成 15 项、每项可独立验收；3D 首期只读且零依赖 |

## 18. 待确认问题

1. **白板默认尺寸**（已定）：**2048×1024**（≈19.6 km/px）——桌面与移动端共用同一默认值，用户可在新建时自由改宽度（§5.1）
2. **比例尺的默认单位**（已定）：**km / AU / 光年** 三档，按 §7.4 的单位注册表实现；自定义单位（里 / 丈）与「世界级度量衡」列为后续可更新功能，届时只需追加单位表条目，不改换算逻辑
3. **尺度预警的阈值**（已定）：默认按地球常识（陆地 15% / 全球 45% / 国家 3000 万 km²），**可按地图调整甚至整体关闭**——三档预设（按地球常识 / 宽松 / 关闭）+ 逐条自定义阈值；关闭只静音「常识判据」，客观读数（实距 / 面积 / 变形倍率）始终显示，详见 §7.7.1
4. **专题图层的比例尺显示规则**（已定）：**要做**，首期落地图层级 + 对象级显示条件，判据用「对象在屏幕上的像素尺寸」（§10.3）；**标签自动避让**列入二期（需要碰撞检测与优先级排版，工作量接近独立子项目）
5. **3D 地球仪的美术方向**（已定）：**要做大气辉光 + 星空背景 + 昼夜明暗**，全部自写着色器实现、零新依赖，三项各可独立关闭，并提供三档性能降级（§14.3）；夜间灯光（陆地掩膜加暖黄噪点）默认关闭、按需开启
6. **触屏长按与绘制的手势冲突**（`touch-action` 与页面滚动、长按呼出快捷菜单 vs 绘制），需在真机上验证后再定交互细节
7. **「网站版负责协作、应用版负责离线」的边界**：应用版的离线编辑是否需要支持先画后同步（涉及 `packages/sync` 的排期）
8. **插件的命名与发布位置**（已定）：包名改用**中性命名 `@worldmap/*`**（`@worldmap/core` / `@worldmap/editor` / `@worldmap/editor-web`，预留 `@worldmap/element`），与主站的 `@create-world/*` 明确切开；**先只在仓库内用**（`"private": true`，不发公共 npm、暂不注册 npm scope），待接口稳定且有外部需求时再决定是否发布
9. **插件是否要做成 Web Component**（已定）：**首期不做，只发 npm 包**；但内核与外观必须彻底分离（不依赖 React Context、不用全局单例），以便将来补一层薄壳即可支持任意框架 / 纯 HTML 嵌入。触发条件与完整优缺点对照见 §15.6.1
10. **3D 美术的默认档位**（已定）：**桌面默认「完整」、移动端默认「精简」**（关大气辉光）；入口在 3D 视图右上角的「显示设置」里，手机用户可自行打开大气辉光或单独开关任一效果，**手动选择优先于自动判定**；偏好按设备记录，不进地图数据
